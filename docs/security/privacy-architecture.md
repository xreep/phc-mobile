# Privacy architecture

## Status
Built · Unit tested — not device validated, not audited by a third party. This document is a
factual description of what the code does, not a compliance certification (see the DPDP section).

## Permissions declared

From `app.json` (the only source of permission declarations in this repo — `android/` is gitignored
and regenerated by `expo prebuild`):

| Permission | Purpose | Scope |
| --- | --- | --- |
| `android.permission.health.READ_HEART_RATE` | Read HR samples from Health Connect | Read-only |
| `android.permission.health.READ_OXYGEN_SATURATION` | Read SpO₂ records from Health Connect | Read-only |
| `android.permission.health.READ_SKIN_TEMPERATURE` | Read skin-temperature delta records from Health Connect | Read-only |
| Location (`expo-location` plugin, `locationWhenInUsePermission`) | Coarse location for weather/AQI; precise location only when sending SOS | Foreground only — `isAndroidBackgroundLocationEnabled: false`, `isIosBackgroundLocationEnabled: false`, `isAndroidForegroundServiceEnabled: false` in `app.json` |

No `WRITE_*` Health Connect permission is requested — the app never writes to Health Connect. No
`ACTIVITY_RECOGNITION`, camera, microphone, contacts, or storage permission is requested. Sending SMS
uses `expo-sms`, which opens the OS composer and does not require a dangerous Android permission
(the OS, not this app, sends the message once the user taps send).

## What is read-only

Every Health Connect record type this app requests (`HeartRate`, `OxygenSaturation`,
`SkinTemperature`) is read-only. Only `requestPermission()` on `react-native-health-connect` is
called with a read scope; there is no write path anywhere in `src/sensors/`.

## Location policy

- **Coarse location** — used continuously (subject to the 30-minute refresh) to look up weather and
  AQI for the phone's city. This is the only location use that repeats.
- **Precise location** — requested only at the moment an SOS is sent, to include a GPS fix and a maps
  link in the emergency message. Never polled, never cached, never sent anywhere except inside that
  SOS message.
- Background location is explicitly disabled in `app.json` on both platforms; the app cannot access
  location while backgrounded.

## What is transmitted

- **OpenWeatherMap requests** — city-level (coarse) location, sent to fetch weather and
  air-pollution data. This is the only recurring outbound network traffic.
- **SOS messages** — either one POST per contact to the Twilio relay (message body + precise
  location, composed entirely on-device) or, via the fallback path, an SMS the OS sends once the
  user taps send in the native composer.

No HR, SpO₂, skin-temperature, or motion reading is ever transmitted, in any code path, to any
server. There is no analytics SDK and no crash-reporting SDK in this build.

## What is stored, and how

Two AsyncStorage keys, both **plaintext, not encrypted** — flagged as a known gap against the PRD's
SQLCipher/encrypted-storage goal:

- `phc.settings.v1` — emergency contacts (E.164 normalised), display name, sharing preferences,
  sensor source. Readable by anything with filesystem access to the app's sandbox (e.g. a rooted
  device or an ADB backup).
- The environment cache — last-known-good weather/AQI snapshot. Low sensitivity (public weather
  data), but shares the same unencrypted store.

No vital reading is stored anywhere; the `SensorReading` ring buffer is React state only and is
discarded when the app is killed. **Planned:** `expo-secure-store` for contacts (P2, see
[`docs/ROADMAP.md`](../ROADMAP.md) M12); an encrypted reading store when persistence lands (M6).

## Secrets policy

No secret is committed to this repository. `.env.local` is gitignored (`.gitignore`); the two
`EXPO_PUBLIC_*` variables it can hold are:

- `EXPO_PUBLIC_OPENWEATHER_API_KEY`
- `EXPO_PUBLIC_TWILIO_SOS_URL`

Both are **public-by-design**, not secrets we failed to protect: Expo's Babel transform inlines any
`EXPO_PUBLIC_*` value into the JS bundle at build time, so anything given that prefix is readable by
anyone holding the APK, regardless of how carefully it is handled beforehand. The OpenWeatherMap key
is a rate-limited weather key; the Twilio relay URL is a public endpoint whose own function — not the
app — holds the real Twilio credentials server-side (see
[`docs/features/sos-relay.md`](../features/sos-relay.md)). **Both must be rotated before a public
APK build**, since the August APK and any development build ship whatever values were inlined at
build time.

## Logging policy

No vital reading, contact, or location is written to the console anywhere in `src/` — verified by
searching for `console.log` / `console.warn` / `console.error` across the source tree outside test
files; none exist. There is no logging framework and no crash reporter wired up, so there is
currently no log-shipping path to audit for PII leakage either.

## Retention and deletion

No reading history exists yet, so there is nothing to retain or delete beyond settings. There is
**no delete-all / factory-reset control in the UI today** — clearing settings requires uninstalling
the app or clearing app storage from the OS. Planned: an explicit "delete my data" control once the
reading store (M6) exists, covering both settings and any persisted history.

## DPDP alignment (principles only — no certification claim)

This section states which architectural choices align with Digital Personal Data Protection Act
principles as a matter of engineering fact; it is **not** a claim of formal DPDP certification or
legal compliance review, which has not been performed (explicitly out of scope per `PRD.md` NG4).

- **Purpose limitation** — vitals are read only to compute the on-device risk score; location is read
  only for weather lookup and SOS.
- **Data minimisation** — coarse location for weather (not precise); only three Health Connect record
  types are requested; sharing preferences default to off except SOS.
- **Storage limitation** — no vital history is retained at all today (the maximal form of storage
  limitation, though it is a side effect of persistence not existing yet, not a deliberate policy
  choice at this stage).
- **User control** — a consent gate on SOS, a sensor-source picker, and per-category sharing
  preferences in Settings.

None of this has been reviewed by a lawyer or a compliance auditor. Treat it as an honest description
of current behaviour, not a regulatory claim.
